# Кривая розжига: перцептуальная кривая и таблица `CURVE_LUT[256]`

> **Задача:** task-1 (F2 research spike). **Статус:** решение реализовано в [`light.cpp`](../LightScheduler/light.cpp) (task-5), таблица из раздела 7 перенесена в код.
> **Исполнение:** task-5 (`light.h/.cpp`) — по инструкции из раздела 9.

## 1. Постановка и принятая стратегия

До внедрения кривой [`light.cpp`](../LightScheduler/light.cpp) поднимал скважность ШИМ **линейно** `0→255`
за `config.fadeDuration`. Субъективно это выглядит как «рывок» в начале (уже 1–2 % скважности
дают заметный свет) и «плато» в конце. Требование заказчика: **50 % воспринимаемой яркости
должны соответствовать ≈30 % скважности ШИМ**.

Решения, зафиксированные PM (выполняются без обсуждения):

* 8-битный ШИМ (`PWM_RES=8`, 0…255) **не меняется**, аппаратура та же;
* кривая — **compile-time таблица** `static const uint8_t CURVE_LUT[256]`, индекс — прогресс
  розжига 0…255 (0 = начало, 255 = конец);
* рантайм — **только целочисленная индексация**, без `float`/`powf`/`expf` в шаге розжига;
* таблица фиксированная, **без UI-настройки кривой**; `Config` не расширяется.

Почему таблица, а не float-формула в рантайме: вызов `powf` был бы вычислительно ничтожен
(≤20 вызовов/с, максимум ~1200 за 60-секундный розжиг, ~1–3 мкс на вызов — меньше 0.01 %
времени ядра 240 МГц). Таблица выбрана ради детерминизма, простоты ревью и полного
отсутствия плавающей точки в горячем пути — не ради производительности.

## 2. Модели восприятия

| Модель | Формула / факт | «50 % восприятия» = какая доля скважности |
|---|---|---|
| Вебер–Фехнер | ψ ∝ ln(I/I₀) — логарифмическое сжатие | для яркости плохо переносится на весь диапазон (логарифм уходит в −∞ при I→0) |
| Стивенс, power law | ψ ∝ Iⁿ, для **яркости n ≈ 0.33** (5° target в темноте; 0.5 для точечного источника) | I = 0.5^(1/0.33) ≈ **12.2 %** |
| sRGB, gamma ≈ 2.2 | кодирование: 50 % кода ↔ 21.4 % линейной яркости | **21.4 %** |
| CIE 1931 L\* | L\* = 116·Y^(1/3) − 16 (Y > 0.008856), Y — относительная яркость; L\* = 50 ↔ Y ≈ **18.4 %** (фотографическая «средняя серая карта» 18 %) | **18.4 %** |

Итого стандартные модели дают **12–22 %** скважности на 50 % воспринимаемой яркости.
Заказчик просит **30 %** — это осознанно «светлее» стандартных кривых: в середине розжига
свет ярче, чем предписывает физиология, зато кривая мягче (меньше «гамма») и проще
воспринимается как «плавно, но не темно». Это отклонение фиксируется в разделе 10,
а калибровка `f(0.5)=0.30` выполняется точно.

## 3. Почему «логарифмическая» кривая не подходит

Нормированная вогнутая логарифмическая кривая

```
f(p) = ln(1 + k·p) / ln(1 + k),   k > 0,   f(0)=0, f(1)=1
```

не может дать `f(0.5)=0.30` **ни при каком** `k > 0`. Доказательство: `ln(1+·)` строго
вогнута, поэтому `ln(1 + k/2) = ln((1 + (1+k))/2) > (ln 1 + ln(1+k))/2 = ln(1+k)/2`.
Деля на `ln(1+k) > 0`, получаем `f(0.5) > 1/2`. При `k→0` предел равен 0.5, при `k→∞`
отношение стремится к 1. Значит `f(0.5) ∈ (0.5, 1)` — **всегда больше 0.5**, то есть такая
кривая «слишком яркая» в середине. Требование `f(0.5)=0.30` требует **выпуклой**
(суперлинейной) зависимости скважности от времени.

Корректная интерпретация «логарифмического» розжига (вариант b): **субъективная яркость
растёт примерно линейно во времени**, а скважность — суперлинейно. Именно это и
реализуется ниже.

## 4. Кандидаты с калибровкой f(0)=0, f(1)=1, f(0.5)=0.30

**A. Степенная (power law), выбрана**

```
d(p) = p^γ,   γ = ln(0.30) / ln(0.50) = 1.7369655941662063
duty(i) = floor(255 · (i/255)^γ + 0.5)      // i = 0..255, округление half-up
```

**B. Экспоненциальная (альтернатива)**

```
d(p) = (e^(a·p) − 1) / (e^a − 1),   a = 2·ln(7/3) = 1.6945957207744073
```

`a` получается из `f(0.5)=0.30`: пусть `x = e^(a/2)`, тогда `(x−1)/(x²−1) = 1/(x+1) = 0.3`,
откуда `x = 7/3`.

**C. CIE L\*/sRGB gamma, «масштабированная к 0.30»** — как самостоятельная кривая не
проходит: обратная к L\* зависимость даёт `f(0.5) ≈ 0.184` (до 30 % скважности она доходит
только на ~62 % прогресса). Любая дополнительная «растяжка» такой кривой до `f(0.5)=0.30`
с сохранением концов сводится к степенному семейству, то есть к варианту A.

## 5. Сравнение через 8-битную LUT

Значения после округления half-up (в скобках — точное значение до округления):

| Индекс LUT | Прогресс | Power `p^1.73697` | Exp `a=1.69460` |
|---:|---:|---:|---:|
| 0   | 0.0 %   | **0** (0.0000)     | **0** (0.0000) |
| 13  | 5.1 %   | **1** (1.4499)     | **5** (5.1771) |
| 26  | 10.2 %  | **5** (4.8331)     | **11** (10.8213) |
| 64  | 25.1 %  | **23** (23.1066)   | **30** (30.4125) |
| 128 | 50.2 %  | **77** (77.0218)   | **77** (76.9456) |
| 192 | 75.3 %  | **156** (155.7680) | **148** (148.1442) |
| 230 | 90.2 %  | **213** (213.1585) | **207** (207.1849) |
| 255 | 100.0 % | **255** (255.0000) | **255** (255.0000) |

Обе кривые монотонно не убывают, концы точные, `LUT[128] = 77` (30.2 % скважности при
50.2 % прогресса; точная формула при `p=0.5` даёт `0.30·255 = 76.5 → 77`).

Различия:

* **Power** темнее в первой половине (`23` против `30` на 25 % прогресса) и «догоняет»
  к концу (`156` против `148` на 75 %). Первый ненулевой duty при округлении half-up —
  индекс **8** (3.1 % длительности); при усечении — индекс 11 (4.3 %), что и указано в
  задании.
* **Exp** раньше выходит из нуля (half-up: индекс **2**, 0.8 %; усечение: 3, 1.2 %) —
  «тлеет» почти сразу, но в первой половине ярче.
* Максимальный **субъективный** шаг у обеих — неизбежный первый переход `0→1` (≈0.158
  воспринимаемой яркости в модели Стивенса n=1/3); остальные шаги ≤0.041. Это ограничение
  квантования 8-бит, а не формы кривой.
* Под «подразумеваемой» моделью восприятия `n = ln(0.5)/ln(0.30) = 0.5757` (см. раздел 6)
  power даёт **почти точную линейность** субъективной яркости: 0.104 / 0.250 / 0.502 /
  0.754 / 0.902 на 10 / 25 / 50 / 75 / 90 % прогресса, тогда как exp уходит вверх в начале
  (0.164 / 0.292) и вниз в конце (0.728 / 0.887).

**Решение: вариант A (power), γ = 1.7369655941662063.**

Обоснование:

1. Это **точная обратная функция** к степенной модели восприятия при калибровке
   заказчика: если `ψ = d^n` с `n = ln(0.5)/ln(0.30)`, то `d = p^γ` даёт `ψ = p` — то есть
   реализует «субъективная яркость линейна во времени» (интерпретация b) без остатка.
2. Одна константа `γ`, одна строка генерации, точные концы и точное `f(0.5)=0.30`;
   минимум кода и максимум ревьюабельности.
3. Меньше света в начале розжига — для «рассвета» это предпочтительнее: дольше остаётся
   тёмным, не «вспыхивает» рано (в отличие от exp, где 1/255 duty наступает на 0.8 %
   длительности, а 5/255 — уже на ~3 %).
4. Экспонента не даёт выигрыша по acceptance-критериям и хуже по линейности субъективной
   яркости в подразумеваемой модели.

## 6. Подразумеваемая модель восприятия и отклонение от стандарта

Калибровка `f(0.5)=0.30` эквивалентна степенной модели восприятия с показателем

```
n = ln(0.5) / ln(0.30) = 0.5757166424934449
```

(проверка: `0.30^0.5757 = 0.5`). Стандартная модель Стивенса для яркости даёт `n ≈ 0.33`;
при ней 50 % восприятия — это `0.5^(1/0.33) ≈ 12.2 %` скважности, а не 30 %. То есть
кривая заказчика **мягче** стандартной: в середине розжига света примерно в 2.4 раза
больше, чем «по Стивенсу». Это принятое продуктовое решение (см. раздел 1), а не ошибка
калибровки; аппаратная проверка «на глаз» вынесена в hardware-чеклист (раздел 10).

## 7. Итоговая таблица `CURVE_LUT[256]`

Формула: `CURVE_LUT[i] = floor(255·(i/255)^1.7369655941662063 + 0.5)`.
Свойства (проверены скриптом из раздела 8): длина 256; `[0]=0`; `[255]=255`;
монотонно не убывает; `[127]=76`, `[128]=77`.

## 8. Offline-генератор (Python)

Скрипт, которым получена таблица. Запускается вручную, **не** в прошивке; результат
копируется в `light.cpp` (task-5). Округление — half-up (`floor(x+0.5)`), чтобы
`f(0.5)=76.5 → 77`; в таблице нет значений ровно `x.5`, поэтому `round()` Python даёт тот
же результат (проверено).

```python
import math

GAMMA = math.log(0.30) / math.log(0.50)   # 1.7369655941662063

def duty(i: int) -> int:
    p = i / 255.0
    return int(math.floor(255.0 * p ** GAMMA + 0.5))

lut = [duty(i) for i in range(256)]

# --- самопроверки (обязательны при перегенерации) ---
assert len(lut) == 256
assert lut[0] == 0 and lut[255] == 255
assert lut[128] in (76, 77)
assert all(lut[i] <= lut[i + 1] for i in range(255)), "не монотонна"

# --- вывод C-инициализатора по 16 значений в строке ---
for row in range(16):
    vals = ", ".join(f"{v:3d}" for v in lut[row * 16:(row + 1) * 16])
    print(f"    {vals},  // {row * 16:3d}..{row * 16 + 15:3d}")
```

## 9. Реализация в task-5 (выполнено: `light.h` / `light.cpp`)

1. Вставить `CURVE_LUT[256]` из раздела 7 в `light.cpp` (файл-уровень, `static const` —
   на ESP32 такое `const` и так лежит во flash, `PROGMEM` не обязателен). Добавить
   `static_assert(sizeof(CURVE_LUT) == 256, "CURVE_LUT: ожидается 256 байт");`.
2. Публичный API **не менять**: `light_setup / light_startFadeIn / light_stop / light_update /
   light_active`.
3. Убрать `float acc` и накопление шага. Хранить `fading`, `fadeStart` (мс) и `lastStep` (мс).
   `light_startFadeIn()`: `fading=true; fadeStart=millis(); lastStep=fadeStart; ledcWrite(0)`.
   `light_stop()`: `fading=false; ledcWrite(0)`.
4. `light_update()` — всё целочисленно:

```cpp
void light_update() {
    if (!fading) return;
    if (millis() - lastStep < FADE_STEP_MS) return;
    lastStep = millis();

    uint32_t elapsed = millis() - fadeStart;
    uint32_t dur     = config.fadeDuration;

    if (!dur || elapsed >= dur) {          // 0 мс или конец розжига
        ledcWrite(PWM_CHANNEL, 255);
        fading = false;
        return;
    }

    // dur ≤ 60000 и elapsed < dur ⇒ elapsed*255 < 15.3e6 (uint32), idx ≤ 254
    uint16_t idx = (uint16_t)(elapsed * 255UL / dur);
    ledcWrite(PWM_CHANNEL, CURVE_LUT[idx]);
}
```

5. Сохранить семантику `fadeDuration`: `0` → максимум на первом шаге (как сейчас);
   `duration < FADE_STEP_MS` → первый же шаг даёт `elapsed >= dur` → 255; в конце —
   ровно 255 и `fading=false`.
6. В комментарии рядом с таблицей указать формулу, `γ` и ссылку на этот файл.
7. `PWM_RES=8`, диапазон 0…255, `config.h` не трогать.

## 10. Отклонение от стандартных моделей, риски, hardware-проверки

* **Отклонение:** `f(0.5)=0.30` вместо 12–22 % по Стивенсу/sRGB/CIE L\* — см. раздел 6.
* **Не проверено на железе** (нет устройства в этой среде): реальная нелинейность
  светодиодной ленты/драйвера, порог зажигания при duty=1…2, субъективная «гладкость»
  на низких уровнях. Это hardware-only проверки.
* **Квантование:** первый шаг `0→1` неизбежно даёт скачок субъективной яркости ≈16 %
  (при n=1/3). Если на железе будет заметно, возможное будущее — 10-битный ШИМ
  (1024×`uint16_t` LUT ≈ 2 КБ) или временное сглаживание (dithering); **сейчас не
  рекомендуется** и не делается.
* **Ограничение индекса:** `elapsed*255` не переполняет `uint32` при `fadeDuration ≤ 60000`
  (верхняя граница слайдера); `idx ≤ 254` в ветке `elapsed < dur`, `255` выставляется
  отдельной веткой. При выходе `fadeDuration` за 60000 нужен `uint64` — маловероятно, но
  отмечено.
